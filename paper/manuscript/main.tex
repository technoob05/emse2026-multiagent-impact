\abstract{\textbf{Context:} A pull request written by one coding-agent product and reviewed by another looks like a multi-agent workflow, but two products on one pull request do not show that either answered the other. \textbf{Objective:} We ask what connected public path follows one cross-product review comment. \textbf{Method:} From one fixed version of the AIDev dataset we analyse 8,608 pull requests where one product reviewed another's change, 546 matched pairs, and a 1,067-request outcome group. Measured activity is anchored to that comment by exact account, comment, and review-batch identifiers. We set aside the first minutes of automated posting, count outcomes only after hour 48 so the exposure precedes the outcome, and re-test the rule with deliberately wrong anchors. \textbf{Results:} Direct dialogue between products is rare; once the opening minutes are set aside, people take most remaining first actions. Cross-product review draws 13 percentage points less visible follow-up than matched same-product review. A reply that GitHub records as answering the comment goes with 17 points more later merging, and a user account writes it four times in five. The wrong-anchor tests then qualify that: a reply attached anywhere else does as well, and shuffling which comment each reply answers leaves the estimate unmoved. Reading all 105 replies, the association sits with those a person wrote, not with one-click hand-offs to another machine. Linking an issue in the request roughly doubles the chance a review point is answered across a product boundary, and changes nothing within one product. \textbf{Conclusions:} Report public multi-agent impact as a map of connections, not a count of products. The trace shows retained human attention, not a resolved review point.}

\keywords{coding agents, multi-agent software engineering, code review, human-agent collaboration, pull requests, mining software repositories}

\section{Introduction}\label{sec:introduction}

On a pull request today you can find two AI coding products at once. One writes
the change. A different one reviews it. It looks like two machines working as a
team, and it is easy to report it that way.

We followed what happens next, one event at a time. Almost none of it is
teamwork. The two products hardly ever answer each other. What we found instead
was a person. A maintainer reads the agent's review point and replies to it.
That reply is rare. It is also the one public connection that goes together with
the change being merged later. A count of products on a pull request measures
none of this.

The question is live. A recent position paper argues that agents can already meet every goal of code
review. On that view, keeping a person as the mandatory reviewer ``is a dead
end'' \citep{monperrus2026endofreview}. Our data speak to that directly. In this
corpus the person is not a formality on top of an agent loop. They are the only
part of the loop that visibly closes.

Before going further it helps to fix the vocabulary, because the whole argument
turns on small details of how GitHub records review. A \emph{pull request}, or
PR, is a proposed change to a project, offered for others to inspect before it is
accepted. Accepting it is called \emph{merging}. People and tools discuss a PR in
three separate places, and GitHub stores them in three separate tables. An
\emph{inline review comment} is attached to one line of the proposed change. A
\emph{review} is a batch: a reviewer looks at the change, writes several inline
comments at once, and submits them together under a single summary, so every
comment in that batch carries the same review identifier. A \emph{PR comment} is
a general remark on the PR, attached to no particular line.

Only inline comments can be answered in a way the platform records. When someone
replies to one, GitHub stores a \emph{reply target}: the identifier of the
comment being replied to. That single stored number is what makes this study
possible, and its absence elsewhere is what limits it.

The gap also matters for measurement, and each of these details is a trap. A short \emph{burst} is many events landing within seconds or minutes of each
other, faster than a person reads. It can look like a conversation when it is
one tool posting its output. A new review can belong to the same submission batch as the
comment it seems to answer, so a tool appears to reply to itself. A user account
can act next simply because it was watching, not because anyone chose it as a
go-between. Mining GitHub has long been known to reward this kind of care
\citep{kalliamvakou2016perils}. If these cases are mixed together, a product count
becomes a weak measure of teamwork.

Field studies already tell us a lot. They count agent-authored PRs, measure how common AI review is, model reviewer
order, trace how agent pull requests reference one another, and study how
developers answer agent comments \citep{li2026aidev,selvanayagam2026a2a,zhong2026agenticreview,
cynthia2026responses,khemissi2026references,duma2026reviews}. Several report that
people still carry the review \citep{zhong2026synergy,chowdhury2026industry}.
Designed systems show how known agents can pass messages, roles, files, or
structured disagreement
\citep{destefanis2026coordinate,qiu2026adversarial,zhang2026reporeviewer}.

What is still missing is a hard test. These studies count who appears, or they
read what was written. Neither tells us whether one actor actually answered
another. Our question is narrower and stricter: after one cross-product review
event, what connected public path can we point at in the data?

We ask four questions:

\begin{description}
\item[RQ1. Is there a handoff?] Once we split one review batch into its parts,
and set aside the fast burst of events that follows a trigger, does anything
left look like one product handing over to another? And who takes the next
visible step? The cost of handing a task between agents has been studied under
controlled interruptions \citep{kc2026handoff}. We ask the question that comes
before it: can a public handoff be seen at all?
\item[RQ2. Who bridges the boundary?] How much public follow-up happens across
the boundary between two products? And when a person steps in, have they worked
on this repository before?
\item[RQ3. Who writes the connection, and does the change get merged later?]
When a reply carries the review comment's own identifier as its target, the
platform itself records what that reply is answering. That is the strictest
connection a public trace offers. Does it go together with the change being
accepted later, and who writes it: another tool, or a person? A looser signal,
an automated action followed by a person acting, covers pull requests where no
reply exists to anchor, and we report it as a check on a wider group rather than
as a second answer.
\item[RQ4. What makes someone answer across the boundary?] A pull request
body often points at an issue, and that pointer gives a reader context the diff
alone does not. It is normally written when the pull request is opened, but the
release records no time for it, so we observe the link rather than its moment of
arrival. Does it change whether a
review point gets answered, and does that depend on who is reviewing?
\end{description}

We make four contributions.

\textbf{An evidence ladder, and a test of its own rungs.} By \emph{evidence
ladder} we mean an ordered set of claims where each step demands more of the data
than the one below, so a study has to say which step it actually reached. Ours
has four steps, which a product count runs together: both products appearing on
one PR, a reply that points at the exact review comment, who takes the next
visible action, and whether the PR is accepted afterwards. The second rung is machine-checkable and strict, which is what
makes the paper falsifiable. We then falsify part of it. Placebo exposures show
that, for predicting a later merge, that strict rung is not distinguishable from a
much looser one: a reply anchored anywhere on the pull request does as well.
Building the ladder and then testing whether its rungs differ is, we think, what a
measurement paper owes its readers.

\textbf{A finding that the ladder produces.} Each rung deletes most of what the
rung above admitted. Almost no cross-product activity becomes one product
answering another. A reply does mark a different later outcome, and a person
writes it four times in five. But reading all of those replies shows that about
one in six is a one-click hand-off to yet another machine, and the association
sits with the rest. What the public trace can show is retained human attention,
not a resolved review point. The measurement choice changes the conclusion, which
is the point.

\textbf{A reusable check for order-based claims.} Reviewer order is often read
as evidence of coordination. We show that shuffling the order of events inside
the same PR reproduces the apparent pattern almost exactly. The nearest prior baseline for an order claim is alphabetical, and it is over files rather than reviewers \citep{bouraffa2025orders}; we
argue a shuffled baseline is the one that can falsify a coordination claim.

\textbf{One lever that survives.} Almost everything that looked like a mechanism
died under a within-repository comparison. One thing did not. A PR that says
which issue it belongs to gets its review point answered about twice as often
across a product boundary, and not at all more often within one product. It is
the cheapest actionable finding we have.

We do not claim the first observation of AI-to-AI review. Full data rules, all
estimates, robustness checks, and rejected experiments are in Online Resource~1
(Supplementary Information).

\section{Related Work}\label{sec:related}

\subsection{Agent work in public repositories}

AIDev maps agent-authored work at GitHub scale \citep{li2026aidev}. Studies of
this and related data examine acceptance, failure, developer roles, merge
conflicts, review signals, and cross-PR references
\citep{pinna2026comparing,ehsani2026fail,cynthia2026roles,xu2026conflict,
nachuma2026review,khemissi2026references}. These studies make clear that
repository context and human participation matter. They also make merge a poor
stand-alone measure of an agent's quality.

Four lines of work sit closest to ours.

\emph{How common it is.} The nearest study counts same-product and
cross-product AI review, comment output, and speed of reply
\citep{selvanayagam2026a2a}. It reports that cross-product review is rare and
very fast. Our burst windows are a way of taking that speed seriously rather
than a new discovery.

\emph{Who reviews, and in what order.} Zhong et al. model ordered human, LLM,
and agent reviewer sequences across review eras \citep{zhong2026agenticreview}.
Bouraffa et al.\ ask whether the order in which a reviewer works through the
files of one pull request is meaningful, benchmarking it against GitHub's
default alphabetical file listing \citep{bouraffa2025orders}. That is a
different order from ours, over files rather than over reviewers, and neither
study compares an observed order against a shuffled one, which is the check we
add.

\emph{Who does the work.} Several studies find that people still carry the
review. Zhong et al. report that developers adopt human suggestions far more
often than agent suggestions \citep{zhong2026synergy}. Chowdhury et al. report a
lower merge rate for PRs reviewed only by an agent than for PRs reviewed only by
people \citep{chowdhury2026industry}. Duma et al. report that most AI-generated PRs in popular repositories get no
review at all, while cautioning that an absent review record is not proof of
absent human oversight \citep{duma2026reviews}. Our RQ3 result agrees with the
direction of this work. What we add is a much stricter definition of what counts
as the human contribution, and a design that keeps it before the outcome.

\emph{Whether agent feedback helps.} Cynthia et al. study how developers
respond to individual agent review comments \citep{cynthia2026responses}, and
Lin et al. mine developer feedback to a deployed agentic reviewer
\citep{lin2026coderabbit}. Fatima et al. find that the quality of reviewer-bot
feedback shows no clear link to workflow outcomes \citep{fatima2026footprints}.
That null is worth holding next to our result: we do not measure whether a
review comment was good, only whether someone addressed it.

\emph{Bots and review participation before agents.} The questions we ask are
older than coding agents. Review bots \citep{wessel2022gatekeepers} and workflow automation
\citep{wessel2023ghactions} both change how a PR behaves. Coverage alone does not explain post-release quality, and participation adds
to it \citep{mcintosh2016mcr}; prior participation is in turn the strongest
indicator of which patches attract no reviewer at all
\citep{thongtanunam2017participation}, and human factors are strongly associated with whether an invited reviewer engages at all \citep{ruangwan2019humanfactors}.
Among pull requests that draw comments at all, the reviewer's first response time is the largest factor in how long the request takes \citep{zhang2022latency},
which is why we place our check point after it rather than before. Our
contribution is to carry those questions across a product boundary that did not
exist when they were asked.

These papers occupy the broad claims that cross-product review exists, that
reviewer order matters, and that people answer agent feedback. Our unit is
different. It is one cross-product trigger, and the exact edges, batches,
owners, and later state that follow it.

\subsection{Reconstructing what a review comment addressed}

Review platforms record replies. They do not record resolutions. A large body of
work therefore recovers the missing link from the code itself, and it is the
route we chose not to take.

Hirao et al.\ recover review links that the platform does not store as
first-class relations, and classify what kind of link each one is with
classifiers reaching F1 between 0.71 and 0.79. It is the clearest
demonstration that recovered edges buy real analytic power at a measurable
error rate \citep{hirao2019linkage}. The code-review-automation datasets take the same
route by assumption, pairing a comment with the next revision of the method it annotated, or of the diff hunk it sat on, to build training triples at a scale no anchored rule could reach \citep{tufano2022pretrained,li2022codereviewer}. Industry does it explicitly.
Google judges whether its \emph{automated} review comments were resolved by
re-running the model on the merged snapshot and asking whether the comment
still fires on the same lines, then confirming a hand-read sample, which puts
resolution near 40\% \citep{vijayvergiya2024autocommenter}, and reports that 7.5\% of all its
reviewer comments are addressed by applying a machine-suggested edit
\citep{frommgen2024resolving}. Closest to our own setting, Sun et al.\ mine more than 22,000 AI review comments across 178 repositories and
adjudicate 4,486 of them, drawn from 51, with a two-stage LLM-assisted framework
that reads the following diff rather than any reply
\citep{sun2026aicodereview}.

We take the other side of this trade on purpose. Our exposure is an explicit
reply on the thread the trigger opened. It is narrow, and every edge it counts
has a named account and a timestamp that comes before the outcome. The cost is
recall: a comment quietly fixed in the next push is invisible to us. But the
alternative has a cost too, and it is the one that would hurt a paper about
measurement. Fregnan et al.\ find that most changes made during review are not
triggered by any reviewer comment at all \citep{fregnan2022reviewchanges}, so a
rule that reads the diff will credit comments for edits they did not cause. Our
errors are omissions. Theirs are false attributions. Since our design places the
exposure before the outcome and then asks how much hidden structure would be
needed to erase it, we would rather miss connections than invent them.

\subsection{Whether the feedback carried signal at all}

A separate literature asks a question we deliberately do not answer: was the
comment any good? Low usefulness is older than coding agents. Bosu et al.\ find
that much review feedback at Microsoft is not useful, that usefulness rises with
reviewer tenure, and that it falls as changes grow \citep{bosu2015useful}; later work predicts usefulness from the comment text and the reviewer's experience \citep{rahman2017usefulness}, and from the comment text alone \citep{ahmed2025useful}. Wessel et al.\ name the failure
mode on the machine side, describing how automated contributions come to be read as noise that overloads and disrupts human conversation \citep{wessel2021noise}. That is our
thesis in an earlier vocabulary: volume is not participation.

The agent era supplies numbers. Sun et al.\ report that between 0.9\% and 19.2\%
of valid AI review comments lead to a code change, depending on the tool, against
60\% for valid human comments in the same repositories
\citep{sun2026aicodereview}. Meta's production system converts 19.7\% of
actionable comments into an applied fix, and its binding constraint turned out to
be where a person sat in the loop: showing patches to reviewers slowed review by
more than 5\% until the interface showed them only to authors
\citep{maddila2026aifixes}.

These studies and ours measure different things, and the difference is worth
stating plainly. They ask whether a comment deserved action. We ask only whether
it got an answer, from whom, and before what. A comment can be excellent and
ignored, or trivial and answered. Our numbers are not comparable to theirs for
the same reason: their denominator is every AI review comment, ours is a
cross-product trigger that opens its own thread. What is striking is that two
literatures built on different units keep arriving at the same place. Whatever
the machine writes, it is the human response that tracks the outcome.

\subsection{Designed multi-agent review}

Role-based systems such as ChatDev and MetaGPT make communication part of the
design \citep{qian2023chatdev,hong2023metagpt}. RepoReviewer divides review into
repository, file, priority, and summary roles \citep{zhang2026reporeviewer}.
Adversarial Review adds a critic that checks a review through structured
disagreement \citep{qiu2026adversarial}. SWE-Review closes the generate, review, revise loop for issue resolution
\citep{wang2026swereview}. Controlled traces can
therefore reveal roles and messages directly.

Public GitHub traces are weaker evidence, but they show real projects rather than
a laboratory. The weakness is specific: seeing two products on one PR does not
show that they shared memory, followed a joint plan, or talked to each other
privately. We therefore keep two names apart for the whole paper.
\emph{Cross-product feedback} is the plain fact that one product wrote review
activity on another product's PR. It is presence, nothing more. \emph{Public
coordination} is the stronger claim that we can point at a connection in the
record: a reply that names what it answers, or a change of hands that the trace
shows. We never let the first stand in for the second, and keeping them apart is
what the rest of the method is for.

\section{Data and Method}\label{sec:method}

\subsection{Data and event anchor}

We pin the AIDev release at revision
\nolinkurl{37bbe1533e26cc1e1374917dba1186d1c8a4dc81}, which gathers roughly 7.6
million agent-authored PRs from six products, with pull requests created through
31 March 2026. The dataset paper describes an earlier release of 932,791 pull
requests from five products \citep{li2026aidev}; the revision we pin is larger
and adds Google Jules, so figures quoted here will not match that paper. From it we take the pull requests whose repository has more than 100 stars,
which leaves 361,296. The release publishes a subset under this name; the count
here is our own reconstruction of that rule on this revision, so a reader
comparing against a published subset size should expect a different number.
Online Resource~1 gives the filter and the per-product counts. A star threshold is a blunt instrument for this. Munaiah et al.\ show that
popularity filters do not measure whether a project is engineered, and build a
classifier over community, continuous integration, documentation, history,
issues, licensing and testing instead \citep{munaiah2017curating}. We use the
star filter because it is the one the release itself applies, and we treat it as
a coarse screen rather than as evidence that every repository here is a serious
project. Its event tables contain submitted
reviews, inline review comments, PR comments, and selected lifecycle events.
PRs are created through 31 March 2026; we use 15 April 2026 at 00:00 UTC as the
common observation boundary.

The six products are Claude Code, GitHub Copilot, Cursor, Devin, Google Jules,
and OpenAI Codex. Each posts under its own official GitHub account, and we map
only those exact account names. A login that merely looks similar is not guessed,
because a wrong guess here would put words in a product's mouth. The PR author carries one product
label. A \emph{trigger} is the first review, inline comment, or PR comment
written by a different product. We take the earliest such event on the PR, and it
must fall after the PR was opened and before it was closed. Everything we measure
afterwards is measured from the trigger. Online Resource~1 gives the full identity registry,
table coverage, joins, and denominators. Inline comments join to a submitted
review by review ID and then to the PR.

An \emph{addressed edge} means one thing only: a later comment stores the trigger
comment's own identifier as its reply target. In plain terms, GitHub itself
records that this comment is answering that one. A reply posted somewhere else on
the same PR does not count, however relevant it reads, because nothing in the data
ties it to the trigger.

One further rule closes a loophole. A reviewer submits many inline comments in a
single batch, and every comment in the batch shares one review identifier. Without
care, a second comment from that same submission could be counted as an answer to the first. That would be a tool appearing to
reply to itself, when in truth both were written at once. We therefore require any later review to carry a different review
identifier from the trigger's.

We checked what that identifier actually points at, because the paper rests on
it. Replies to an inline comment are grouped under it in what GitHub calls a
\emph{thread}: the original comment, then everything written in answer to it,
shown together beside the line of code. GitHub sets the reply target to the
\emph{first} comment of that thread, not to whichever comment came just before. The release agrees: across
88,907 inline replies, not one names a comment that is itself a reply, so reply
threads are one level deep. An addressed edge is therefore \emph{a reply in the
thread that the trigger opened}. Section~\ref{sec:threats} reports what that costs us, which turns out to be very
little in this cohort. Figure~\ref{fig:contract} shows the anchor, the three
exclusion rules, and the four evidence levels that the rest of the paper keeps
separate.

This precision has a price, and the reader should know its size before reading
any result. Only inline review comments carry a reply target. A review summary
and a comment on the pull request itself carry none, so no exact edge can ever be
built for them, whatever threshold we choose.

Across all 8,608 pull requests where one product reviewed another product's
change, inline comments are 42.9\% of everything a reviewer writes; the other
57.1\% arrive through those two unanchored channels. Counted per pull request
rather than per comment, 4,824 of the 8,608 (56.0\%) have an inline comment as
the first cross-product review and are therefore in scope. The other 44.0\% are
not measured here at all.

We take that trade deliberately. A rule that never fires wrongly on 56\% of
cases is worth more to a measurement paper than a looser rule that reaches all of
them and cannot say which of its matches are real. Online Resource~1 reports the
full channel breakdown, and Section~\ref{sec:threats} returns to what the unseen
share might hold.

reconstruct how they relate. Two of them are not stages in one chain. The

\subsection{One design per question}

A \emph{relay} is the handover we are hunting for: the next visible step on the
PR is taken by a \emph{different} product from the one that wrote the review
comment. We use it as our operational definition of a public handoff: one product raises a
point, and a different one acts on it where the record can show it. That is a
narrow definition on purpose. Two tools could coordinate through a shared plan,
an external orchestrator, a generated patch, or a person in between, and none of
that would leave this trace. RQ1 asks how often the public handoff itself
happens, not how often coordination of any kind does.

For RQ1, we follow each first cross-product trigger for seven days, ending at
PR closure when earlier. We join exact replies, new review rounds, later PR
comments, and visible force-push events. The first later owner is a user
account, mapped product, other bot, branch movement or untyped activity, or no
action. We then repeat the whole calculation while ignoring everything in the first 0, 1,
5, 10, or 30 minutes after the trigger. The reason is the burst problem above.
Automation posts within seconds, so if we simply take the next event we will
usually be reading a machine finishing its own output rather than anyone
responding. Waiting a few minutes before looking is a crude but honest way to ask
who acts once that first rush is over. It does not tell us where one tool's run
ended; nothing in the public record does. We then wait a second five minutes, to
check whether a PR whose first post-burst actor was a product genuinely goes on to
a \emph{different} product, which would be a real relay.

For RQ2 we build matched pairs. Each cross-product trigger is paired with a
same-product trigger from the same repository, the same PR-author account, the
same author product, the same source channel, and the same month. Pairing uses
nearest time without replacement.
We also identify the first distinct user account within 48 hours. Prior public
history requires that account to have submitted a review in the same repository
on a different PR strictly before the trigger.

For RQ3 we fix a check point at hour 48 after the trigger. The reason is timing.
If we simply asked whether answered PRs merge more often, a reply that arrived
\emph{after} the merge would count in its favour, which is backwards. So we keep
only PRs still open at hour 48, ask whether a reply had arrived by then, and count
merges only from that moment on. Cause is kept before effect by construction.

This costs us most of the population, and we would rather say so than hide it.
Most cross-product inline-trigger PRs are finished before hour 48, so they never
enter this group; we report how many alongside the result. A PR also needs 30 full
days of later observation to be included, so nothing near the end of the data
window can quietly count as unmerged.

A second, looser cohort sorts the first 48 hours by what visibly happened: a
person acted first, automation acted and then a person did, automation acted with
no person following, the branch moved, something else happened, or nothing did.
This is how we compare an automation-to-person handover against automation on its
own.

For RQ4 we ask about the issue link: whether the pull request description points
at a numbered task in the project's tracker, of the kind that is meant to give a
reader the task context. We read it as context the reviewer had, which is how
such links are normally written, but that reading is an assumption and not
something we can check. The release records no timestamp for the
description, and descriptions can be edited, so what we observe is a link present
when the data were collected. Section~\ref{sec:threats} says what that costs. An issue is a numbered task in the project's own
tracker saying what the change is for. The outcome is whether the review point gets answered
within 48 hours.

Two choices matter here, and both are about making the comparison fair. First, we
rebuild the outcome from the raw comment table for cross-product and same-product
triggers alike. The event tables we built for the cross-product side simply do not
cover the same-product side, and comparing a carefully built number against a
differently built one proves nothing. Second, we keep only triggers that open
their own discussion thread. A comment posted into an existing thread can never
receive an addressed edge, because replies in a thread point at whichever comment
started it. Including such triggers would compare cases where the outcome was
possible against cases where it was impossible by construction. This barely
touches the cross-product side and removes nearly half of the same-product side,
which is precisely why it has to be done. We then compare the two kinds of
reviewer inside the same repository and the same month.

We report percentage-point contrasts because they are easy to read, and because a
point difference in probability is what a practitioner can act on. Being precise
about how they are produced matters more than the phrasing, so the estimator is
written out here.

Every outcome model is a linear probability model fitted by ordinary least
squares, with standard errors clustered on the repository. The unit is one pull
request. For the RQ3 result the equation is
\begin{equation}
\label{eq:rq3}
\Pr(M_i = 1) = \beta_0 + \beta_1 E_i + \gamma' X_i,
\end{equation}
where $M_i$ is one if pull request $i$ merges after hour 48 and within 30 days,
$E_i$ is one if a reply naming the trigger arrived by hour 48, and $X_i$ holds
everything visible before the trigger: the authoring product, the reviewing
product, and the calendar month as sets of indicators, the age of the pull
request at the trigger on a log scale, the count of earlier public events on the
same scale, and separate counts of earlier user events, earlier automated events,
earlier decisive reviews, and earlier force-pushes. The estimand is $\beta_1$: the
difference in later-merge probability between answered and unanswered pull
requests, among those still open at hour 48, holding the pre-trigger record fixed.
It is an association, not an effect.

The RQ4 model is the same family with an interaction. It regresses whether the
review point is answered within 48 hours on an issue-link indicator, a
cross-product indicator, their product, and absorbed repository and calendar-month
indicators; the estimand is the coefficient on the product term. RQ2 needs no
model: it is a paired difference over matched pairs.

Uncertainty comes from resampling whole repositories with replacement, because
pull requests inside one repository share people and policy. Permutation tests
shuffle the label of interest inside the repository and refit. Draw counts and
seeds for every interval and every test are in Online Resource~1, which also
carries the full covariate list, the matching rule, and the pre-trigger balance
after matching. We vary the reply window from one to 48 hours, add repository
indicators, and remove each ordered product pair in turn.

The later-state comparison comes from watching, not from an experiment, so a
large part of our effort goes into trying to break it. Six checks do that, and
the Results section reports each one where it belongs. Two of them ask how strong
an unmeasured cause would have to be: an E-value \citep{vanderweele2017evalue},
which puts a single number on that strength, and a grid showing the same thing as
a region. Two more attack the exposure itself, by moving the reply's anchor to a
different comment and by shuffling which comment each reply is anchored to. The
last two attack the design: one drops the hour-48 rule and follows every trigger
PR over time, and one applies the model to outcomes that had already finished
before the trigger, where nothing should be found.

All six put a limit on fragility. None tells us what an intervention would do.
Task difficulty and maintainer intent are not measured here, and either could
shape both the public path and the outcome.

\subsection{Reproducibility and AI use}

The artifact pins the data revision, stores PR-grain cohorts, generates all
tables and figures, and runs automated data and leakage checks. We also screened
current public review and agent-trace datasets against the same event contract.
A separately published cohort of agent-to-agent review lets us check our product
labels and event times on pull requests both studies happen to cover. We also
applied our exact identity, reply-target, overlap, and hour-48 rules to a large
public corpus of agent review conversations. External rows are not pooled with the main cohort.
OpenAI Codex helped inspect data, write and test analysis code, search
literature, make figures, and edit the draft. The authors checked source
records, reran the analysis, verified cited sources, and reviewed the text and
figures. Human authors remain responsible for every claim, citation, and final
decision. No model is an author.

\section{Results}\label{sec:results}

\subsection{RQ1: product presence rarely becomes a relay}

Two products on one PR almost never becomes one product answering the other.
Once the fast automatic burst is set aside, a person usually takes the next
visible step.

Before the numbers, two sets of names. The narrowing in Panel A of
Figure~\ref{fig:topology} runs through four rules, each stricter than the last:
both products act on the same pull request; anything at all happens afterwards; a
later comment names the trigger as what it answers; and that answer comes from a
product other than the one that raised the point, which is the handover a
multi-agent workflow would leave behind.

Panel B sorts whoever acts next into four kinds. A \emph{user account} is an
ordinary GitHub account rather than one we recognise as a coding product. A
\emph{mapped product} is one of the six named above, acting under its official
account. \emph{Other bot} is automation we cannot attribute to any of the six.
\emph{Branch movement or untyped activity} means the change moved but nobody
wrote anything we can classify. Shares are taken among the pull requests that
still have an action left after the waiting period, so they do not sum to a
hundred. Later public
activity is common. An exact reply from a product different from the
triggering reviewer is not: it appears on fewer than 1\% of PRs. User accounts
write four in five of those exact replies.

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{Fig2.pdf}
\caption{Public activity narrows before any connected edge appears. Panel A
counts the pull requests surviving each stricter rule, from all 8,608 where one
product reviewed another product's change. Panel B shows who acts next once the
opening rush of automated events is set aside, for five waiting periods; the
four actor kinds are defined in the text above. At a five-minute wait, 4,771
pull requests still have an action left. The waiting periods are our test
settings; nothing public says where one tool's run ended.}
\label{fig:topology}
\end{figure}

The burst test changes the owner, not only the time. After five minutes, mapped
products lose close to a third of their mapped-first classifications. User
accounts then own far more of the remaining actions than mapped products do. This
ordering holds in every leave-one-repository-out and leave-one-product-pair-out
check.

Five minutes is a convention, and we should not pretend otherwise, so we went
looking for a boundary in the data. There is not one. The time from a trigger to
the next event climbs smoothly to a single peak around four minutes with no
separate machine spike before it, so a rule that looks for a valley between two peaks finds nothing to select,
either globally or for any single product. A change-point rule always returns some number, and it returns roughly
one minute; per-product versions of it range from under a minute to about nine,
with intervals wider than the global one. Fitting the window per product makes it
less stable, not more.

What matters is that the conclusion does not depend on the choice. We tried nine schemes in all: the five fixed windows, two global cuts chosen by
the change-point rule, one unrestricted and one confined to the burst region, and
the same two rules applied per product. In every one of them, user accounts are the most
common post-burst owner and stay ahead of the products, with an interval clear
of zero. The
size of the lead moves a good deal, from 19 to 41 points, and the direction never
does. So we report the window as a stated convention that the result survives,
rather than as a discovered boundary.

The next step is even more selective. Among PRs that are still mapped-product
first after five minutes, only about one in twenty move next to a different
mapped product after a second waiting period.

The same product carrying on is far more common, and it is tempting to read
that as an agent staying with the task. It is not. We shuffled the order of
the later events inside each PR, keeping that PR's own mix of products, and
the shuffled data reproduce the pattern almost exactly. So the trace supports
one thing only: a relay to another product is rare. It gives no support for a
special product-persistence mechanism.

\noindent\textbf{Answer to RQ1.} Two products on one PR greatly overstates how much handing over really happens. Once the fast burst of events is set aside, user accounts are the main visible owner. A relay to another mapped product is rare.

\subsection{RQ2: familiar user accounts bridge a quiet boundary}

\begin{figure}[!htbp]
\centering
\includegraphics[width=\linewidth]{Fig3.pdf}
\caption{A quieter boundary, and a history common on both sides of it. Panel A
shows all six matched outcomes twice: on the left how often each happened, with
the filled mark for the cross-product side and the hollow mark for the
same-product side; on the right the difference between them with its 95\%
interval, against a line at no difference. Only the top row's
interval clears that line, and the dashed rule separates it from the five that do
not. The starred row uses the 241 pairs where a reply is reachable on both sides.
Panel B asks how often whoever steps in had reviewed in that repository before,
under three ways of choosing whom to count.}
\label{fig:bridge}
\end{figure}

The cross-product boundary is a quieter one. Comparable triggers get less
visible follow-up across it, and when someone does step in, it is usually a
person who has reviewed in that repository before.

Visible follow-up is less common after a cross-product trigger than after its
matched same-product partner. The gap is 13.4 percentage points
(Figure~\ref{fig:bridge}A). No other outcome supports a claim that this
quieter boundary leads to more branch movement or more merges.

One of those outcomes needs a different denominator, and saying why matters more
than the number. Whether the review point itself gets a reply can only be
observed when the trigger opens its own inline thread, since that is the only
case where GitHub records what a reply answers. The 546 pairs fall into four groups. On 293 the trigger is a review summary or a
comment on the pull request, so no reply can be recorded for either side. On one
pair both triggers sit mid-thread, which blocks both sides as well. On 11 the
cross-product trigger opens a thread and its matched partner does not, so the
outcome is possible on one side only, and every one of those 11 runs the same
way, pulling the comparison towards zero from a single direction. That leaves 241
pairs where a reply is reachable on both sides. We therefore estimate
that row on the 241 pairs where a reply is possible on both sides, where the gap
is $-3.3$ points rather than $-0.9$, still with an interval that spans zero. The
other five outcomes do not depend on thread position, and we checked that the
broadest one never rests on an anchored reply alone.

That average hides something a reader should know. The 546 pairs are not spread
evenly: one repository supplies a fifth of them, and one ordered pair of products
supplies more than a quarter.

We fixed a rule in advance for what would count as a general finding: the gap must
stay negative when any single repository is dropped, stay negative when any single
ordered product pair is dropped, and be negative in at least two thirds of the
pairs large enough to estimate on their own. It passes all three. The direction,
then, is general by our own standard.

The size is not, and that matters more than the verdict. Six ordered pairs are
large enough to estimate separately. The two largest gaps, near $-20$ and $-26$
points, are both on pull requests written by the same product, and the remaining
four sit within about six points of zero. Only one pair has an interval that
clears zero on its own. So the boundary is quieter in general, but how much
quieter depends heavily on whose pull request it is. Online Resource~1 gives the
full composition and every per-pair estimate.

Figure~\ref{fig:bridge} joins the matched comparison with a wider history
check. Seven in ten of the first user-account bridges had already reviewed
another PR in that repository. That rate is close to the rate among all users
who answered within 48 hours. So prior history is common right across the
response layer. It does not tell us why one account rather than another
becomes the bridge.

\noindent\textbf{Answer to RQ2.} Comparable cross-product feedback has less
public follow-up. When a user account becomes the visible bridge, it is usually
not a repository newcomer, but the trace does not show deliberate expert
routing.

\FloatBarrier
\subsection{RQ3: a person writes the edge that marks a later state}

\begin{figure}[!htbp]
\centering
\includegraphics[width=\linewidth]{Fig4.pdf}
\caption{What a reply is worth, and what its anchoring is not. Each pull request
sits in the lowest band it qualifies for and moves up when its own first reply
of that kind arrives, so no time before a reply is credited to it. Shaded bands
are 95\% intervals from resampling repositories. For the first two and a half
days the silent curve is highest: a pull request still being replied to has not
merged yet. The two reply curves overlap at all 73 grid points, so where the
reply is anchored does not separate them.}
\label{fig:relay}
\end{figure}

Among the slower PRs that are still open at hour 48, one signal stands out as a
marker of later merge: somebody replies. Four times in five that somebody is a
person. What we did not expect, and report below, is that the precise part of our rule adds nothing to the prediction. That part is the
requirement that the reply hangs on the trigger's own thread.

The group holds 1,067 inline-trigger PRs. It is the slower-moving part of the
population. Most cross-product inline-trigger PRs close, and most of those
merge, at or before hour 48. Our group is the 27\% that are still open when
the outcome window opens. Everything below describes that slower group, not
the most common kind of cross-product PR.

The exposure also needs naming precisely. The rule is a reply whose stored reply
target is the trigger's own identifier. It does not require another
product to write that reply. Across the 128 exposed reply events, 105 come from ordinary user accounts. The
triggering product replies to its own comment 13 times, seven come from bots we
cannot attribute to any product, and only three come from a mapped product other
than the one that wrote the trigger. So the connected
signal here is a person acknowledging an agent's review point. It is not a
conversation between agents.

Later merge is more common when there is an exact reply to the trigger than when
there is none: 55\% against 37.9\%. After adjusting for what was already
visible before the trigger, the difference is 17.3 percentage points.
It stays positive for reply windows from one to 48 hours, in a model that only
compares PRs inside the same repository, and after removing each ordered product
pair in turn. We also tested it against a harder comparison. Instead of an edge
versus silence, we compared an exact edge with PRs that already carry other
public discussion. The result stays positive.

\paragraph{The anchoring is not what carries it.} We built the strictest
connection the trace allows, so the first thing to ask is whether the strictness
is doing any work. Two placebo exposures answer that, and they do not answer it
the way we hoped.

The first keeps the reply and moves the anchor. Take the PRs where a reply landed
somewhere else on the pull request, not on the trigger's thread. That is still somebody active in review, so some association is expected. To
compare the two like for like we put both in one model, against the same
reference group of pull requests with no inline reply at all. The off-target
reply is 17.9 points and the exact edge 18.9, so the gap between them is one
point, with an interval running from $-13$ to $+15$. Fitting each exposure
separately on its own support, as Online Resource~1 also reports, gives 17.5 and
17.3; the two framings agree that the anchoring buys nothing, and the joint model
is the one that licenses subtracting them. The second is harsher. Hold the reply events fixed and shuffle which comment each
one is anchored to. If the anchoring carried the signal, that should knock the
estimate down. It does not move. We had pre-specified shuffling inside repository
and month, but too few PRs can move under that rule for the result to be readable,
so we report the calendar-month version, where every PR can move. Its null centres
on 16.8 points and our observed 17.3 sits in the middle of it rather than out in
the tail. Every other stratification we tried agrees.

A third control, which we ran to check the design rather than the exposure, does
behave. Give each PR a fake reply time drawn independently of its own history and
apply the identical hour-48 rule, and the estimate collapses to zero. So the
timing rule is not manufacturing a contrast out of nothing. The problem is not the
estimator. It is what the exposure means.

\paragraph{What the reply says does matter.} If the anchor is not the active
ingredient, something else must be. We read all 105 user-written replies and
sorted them with a rule set fixed in advance: platform text, a hand-off to another
automation, a short acknowledgement, or a substantive response. About one in six is a routing click: \texttt{@copilot fix this}, or GitHub's own
``apply changes based on this feedback'' button, whose words belong to the
interface rather than to the person. Fifty-nine of the 105 replies are
substantive, and they fall on 56 pull requests.

Those 56 pull requests carry the whole result. Restricting the exposure to them
leaves the estimate where it was, at 16.8 points, on half as many exposed PRs. The
routing replies give 8.7 points on an interval that spans zero, and the PRs behind
them merge slightly less often than the exposed group as a whole. With fifteen
such PRs we cannot separate the two subsets statistically, so we do not claim that
a routing click is inert. We claim only what the numbers support: the substantive
half alone reproduces the headline.

Putting the two together changes what we think we measured. The addressed edge is
not a record that a review point was resolved, and it is not a special kind of
connection. It marks activity from an account we classify as a user account, returning to the
pull request within 48 hours with something substantive. Our account-level
screening finds almost all of these accounts behave like people rather than
scripts, but the account is what we observe and the person is what we infer from
it. Where that attention landed on the page turns out
not to matter. That is a smaller claim than the one we set out to make, and it is
the one the data support.

It also tells us what the strict rule was worth. It did not predict better than a
loose one. It did let us name the account behind every edge and read what that
account wrote, which is how we found the routing clicks at all. Precision bought
us attribution, not power, and for a paper about measurement that is the more
useful purchase.

Because most exposed replies are written by people, we refit the model under
two stricter rules for what counts as an edge. One drops replies written by the
triggering product itself. The other keeps only replies from a user account.
Both give the same answer, with intervals that stay clear of zero. The result is
a property of the addressed edge, not of a product answering itself. Only three PRs carry an exact reply from a mapped product other than the
trigger's. That is far too few to model. The count is the RQ1 finding showing up
again at the outcome stage.

The exact edge is not the only visible thing that goes with a later merge. A
wider model that puts all four post-trigger states side by side shows a small
group of PRs with branch movement and no discussion sitting even higher, on a
very wide interval. Any visible sign that a PR is still being worked on points
the same way. We report that model in Online Resource~1 and keep the harder
discussion-only comparison as our main specificity check.

The looser signal promised above gives a check on a wider group. Where no reply
exists to anchor, we can still ask whether an automated action was followed by a
person. Pull requests where it was are linked to 12.9 points more later merge
than pull requests where automation acted with nobody following, after the same
pre-trigger adjustment. That comparison has its own cohort and its own reference
group, so the number is not interchangeable with the 17.3 above; it says only
that the pattern survives where the strict rule cannot reach.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\linewidth]{Fig5.pdf}
\caption{What a hidden cause would have to be. A factor we never measured could
explain the result away only if it were both far more common among answered pull
requests, on the horizontal axis, and shifted later merging a long way on its
own, on the vertical axis. The shaded corner is where it would have to sit; the
dashed line marks the weaker feat of widening the interval past zero. The four
dots are the factors we did measure, plotted by size on the same axes. This is
bias arithmetic, not proof that no such factor exists.}
\label{fig:sensitivity}
\end{figure}

Figure~\ref{fig:sensitivity} asks how fragile that result is. The worry is always
the same with observational data: some factor we never measured might be driving
both the reply and the merge. We cannot rule that out, but we can say how strong
such a factor would have to be. That is what an \emph{E-value} does
\citep{vanderweele2017evalue}. It asks: how strongly would a hidden factor need
to be tied to \emph{both} the reply and the merge, over and above everything we
already control for, before it could account for the whole result? The E-value is defined on the risk-ratio scale
\citep{vanderweele2017evalue}, and our estimate is a difference in
probabilities, so we convert: we divide the adjusted difference by the
later-merge rate among unanswered pull requests to obtain a risk ratio, then
apply their formula to it. That conversion is ours. It is not the
population-standardised procedure the authors implement for risk differences,
and a reader who prefers that procedure should treat our figure as approximate. Here the answer is 2.27, and 1.67 at the interval
limit. Roughly speaking, such a factor would have to be more than twice as common
among answered pull requests as among unanswered ones, and more than double the
chance of a later merge on its own. The figure shows the same question as a map: the shaded corner is where such
a factor would have to live, and it is a demanding corner to reach.

A shuffle test gives a second check, one that rests on the design rather than
on a formula. We keep only repositories that hold both kinds of PR. Inside each
one we shuffle the exposure label many times and refit. The shuffled results
centre on zero, and the real result sits far out in the tail ($p=0.007$,
two-sided). So the finding does not rest on the standard interval formula.

The last check is the weakest, and it half fails. The idea is simple. We take
three things that had already happened \emph{before} the trigger, and ask the
same model whether an answered pull request differs on them. They are: someone
had already approved the change or asked for changes; the branch had already been
rewritten; and a person had already been active on the pull request. The trigger
cannot reach back in time, so a well-behaved analysis should find no difference on
any of them.

The first two behave, sitting on zero at every reply window. The third does not.
Pull requests that a person had already touched are somewhat likelier to be
answered later, and at the shortest reply window that difference is big enough to
be real.

That is specific rather than fatal. It means answered PRs were already somewhat
different PRs, and our controls do not remove all of that difference. The lean
bites hardest at the shortest window, which is one reason 48 hours is our main
window rather than one hour. At 48 hours it is small and its interval includes
zero, so we call it an estimate rather than a clean pass. Online Resource~1 prints
all three.

Two further checks matter more than any of the bounds above, because they attack
the design rather than the arithmetic.

The first drops the hour-48 rule and asks what the whole population looks like
over time. Figure~\ref{fig:relay} follows every cross-product inline-trigger PR
from its review comment, counting a PR as unexposed until its own reply arrives.
Two things are visible there that a single contrast hides. The curves cross
early, because a PR that is still being replied to has not merged yet. And most
of these PRs merge either way, so by day 30 the gap is a few points rather than
the seventeen the hour-48 group shows. The direction survives. A separate discrete-time hazard model, fitted on the
whole population by pooled logistic regression over daily risk periods with a
baseline for each period and standard errors clustered on the repository, estimates a discrete-time merge hazard. Its odds ratio on the reply indicator is
about 1.74, so the odds of merging in the next period are roughly that much
higher while a reply is active. That figure barely moves as controls are added, from 1.73 with the
baseline alone to 1.74 with the full pre-trigger set, across 3,940 of the 3,942 pull requests, in 893 repositories. Two contribute no
risk period at all, because their follow-up time is zero, so the hazard model
has nothing to fit on them; the cumulative curves keep all 3,942. Online Resource~1 carries the specification. The large
hour-48 contrast is specific to that slower-moving cohort.

The second asks who wrote the edge. We split the exposed PRs by whether the
replier had already reviewed in that repository before the trigger. Almost all of
the association sits with the familiar repliers, and a reply from someone new to
the repository shows no positive link at all. That looks like a mechanism, and we were tempted to report it as one. It does not
survive the obvious check. When the comparison is held inside a single
repository, the gap between the two kinds of replier shrinks to near zero with an
interval that spans it.

We then tried to name what the repository is standing in for, because a fixed
effect that explains everything and means nothing is not a satisfying place to
stop. Repositories where familiar repliers dominate really are different: they
run about six times as many reviews per pull request and merge roughly twice as
often as repositories where newcomers dominate. But putting those measured
differences into the model removes less than a fifth of the gap, while the
repository indicator alone removes nearly four fifths. Whatever the repository is
carrying, it is not review intensity, merge rate, volume, contributor count, or
age. We can show the shape of the thing and we cannot yet name it, so we say so. Familiar repliers and newcomers are mostly in
\emph{different repositories}, and those repositories differ in how often
anything gets merged. We therefore report the split as a description of where
the signal sits, not as evidence that knowing the repository is what makes the
reply work.

An exact reply may mark a clearer issue, an engaged maintainer, a useful
comment, or another unmeasured condition. The data do not tell us which. The
result supports the value of a connected trace as a field signal; it does not
show that adding a reply would cause a merge.

\noindent\textbf{Answer to RQ3.} Among pull requests still open 48 hours after
the trigger, a person replies, and the reply goes with a later merge. That
conditioning matters: the group is the slower-moving quarter of the population,
and the 17-point figure is a conditional association inside it rather than an
effect anyone should expect across all cross-product review. Four times in five it is a user account rather than an agent. But the
exact anchoring we built the study around is not what carries the association: a
reply anchored elsewhere on the PR does just as well, and shuffling the anchor
leaves the estimate unchanged. Reading the replies shows where the signal does sit: with the ones a person
wrote themselves rather than routed onward. So the
measure marks retained human attention, not a resolved review point. Nearly all
of the association sits with repliers who already review in that repository, but
that split is between repositories rather than inside them, and our measured
repository descriptors do not explain it. Nothing here is causal.

\FloatBarrier
\subsection{RQ4: task context matters only across the boundary}

An issue link changes nothing when the reviewer is the same product. It roughly
doubles the chance of an answer when the reviewer is a different one.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\linewidth]{Fig6.pdf}
\caption{Whether naming an issue helps depends on who is reviewing. Panel A follows pull requests reviewed by the product that wrote them and those
reviewed by a different one, with the count behind each point. Within a product
the line is flat; across a boundary it climbs. The dotted line is not data. It marks where the cross-product group would have
landed had the link moved it as much as it moved the same-product group, and the
arrow measures the gap to where it actually landed: 17.1 points, the raw
contrast. Panel B reports that contrast after comparing inside the same repository and
month, giving 13.3 points with its interval; the hollow mark is the raw 17.1,
and the pale band the range left when any one repository is dropped. Both panels
keep only triggers that open their own thread. These are links in observed data,
not causes.}
\label{fig:context}
\end{figure}

Among triggers that open their own thread, a same-product review point is
answered about a fifth of the time whether or not the PR points at an issue.
A cross-product review point is answered 12.7\% of the time without a link and
28.3\% of the time with one (Figure~\ref{fig:context}). The difference between
those two differences is 13.3 percentage points (95\% interval: $4.4$ to
$22.2$) once we compare inside the same repository and the same month.

We tried to break it. The estimate holds when the month is dropped and when each of the fifteen most
influential repositories is removed in turn, which leaves a range of 11.4 to 16.1
points. It also holds when mid-thread triggers are put back in. That check keeps
the outcome definition exactly as it is, so those triggers enter the denominator
carrying an outcome that cannot occur for them; the estimate falls only slightly,
to 12.1 points, consistent with dilution from adding structurally impossible
cases. Shuffling the link label inside each repository, the way we shuffle
event order in RQ1, gives a reference distribution centred on zero against which
the observed value sits far out in the tail ($p=0.001$).

The direction is not new on its own. Issue linkage is already known to relate to
how agent-authored PRs fare, while showing no such relation for human-authored
ones \citep{yoshioka2026meaningful}. What is new here is that the link is not
really a property of the pull request. It is a property of the boundary being
crossed. The same link, on the same kind of PR, does nothing when the reviewer
shares the author's product and a great deal when it does not.

That fits what is known about how people read a review. References in a PR
discussion are how participants build common ground \citep{chopra2021referencing},
and reviewers begin by orienting themselves to context and rationale before they
decide anything \citep{heander2026decisionmaking}. Inside one product the loop
can close without that work. Across the boundary somebody has to reconstruct why
the change exists, and a link to the issue is the cheapest way we can observe of
handing them that.

\noindent\textbf{Answer to RQ4.} An issue link observed in the pull request body goes with more answered review
points across a product boundary, and with none within one product. What we
observe is the link as the data record it, not proof that it was context the
reviewer had beforehand, and we cannot say the link causes the answer. PR bodies can be edited, and the release carries no timestamp
for the link, so we cannot prove every link was present before the trigger.

\section{Discussion}\label{sec:discussion}

\subsection{The unit of measurement is the problem}

Ask how much multi-agent software engineering is happening and you will be
handed a count of products. That count is not a small overestimate. It is the
wrong object.

A count answers ``who appeared''. The thing anybody actually cares about is
``what connected''. Those two come apart almost completely here. Two products share a pull request 8,608 times. In 74 of those, fewer than one
in a hundred, one answers the other's review point where the record can show
it. Everything in between is real activity that never becomes a connection: the
reviews, the comments, the branch movement.

Once you insist on a connection, the multi-agent story turns into a human one.
The reply on an agent's review point is written by a person four times in five.
That person is usually not new to the project. Some of the time, though, what the
person writes is a hand-off to yet another machine, and those are the replies
that do not go with a later merge. This is the part a product count
cannot see, and it is the part that goes together with the change landing.

\subsection{What we could not show, and why it matters}

The most interesting thing we found is something we then had to give up. So, in
the end, was part of our own headline.

We built the study around an exact anchor: a reply that names the trigger comment
as its reply target. It is the strictest connection a public trace allows, and we
expected the strictness to be the reason the result held. It is not. Move the
anchor to any other comment on the same pull request and the association is the
same. Shuffle which comment each reply hangs on and the estimate does not move.
What predicts a later merge is that a person came back within 48 hours and paid
attention, not where on the page the attention landed.

We could have reported the anchored number alone and nobody would have known. It
is worth saying why we did not. The claim we would have been making is that
answering a specific review point is what moves a pull request forward, and that claim would have supported a piece of advice our own data do not support,
namely to build tools that anchor agent feedback precisely. The anchor still earns its place,
but for a different reason than we assumed. It is what let us name the account
behind every edge and read what that account wrote, and that is how we found the
routing clicks. Precision bought attribution, not prediction.

Splitting the answered review points by whether the replier already reviews in
that repository produces an enormous gap. It looks like a mechanism: familiarity
is what lets a person pick up an agent's review point. Hold the comparison
inside a single repository and the gap collapses. Familiar repliers and
newcomers are mostly in different projects, and those projects differ in how
often anything gets merged at all.

We report this because the same trap is waiting in most of this literature. A
between-project difference dressed as a personal one is easy to produce and hard
to notice. Two cheap habits caught it here and would catch it elsewhere: compare
inside one repository, and shuffle the label you think is doing the work. Our
apparent product persistence died the same way, to a shuffle of event order
inside the very same pull request.

These were not the only casualties. Repeated automation looked like it escalated
to a person, until the same shuffle reproduced it. Ownership looked like it moved one
way from products to people, until we looked at both directions. Prior review
history looked like it bought a merge advantage, until we compared inside one
repository. Review requests looked like deliberate routing, until we found the
exported event does not say who was asked. Two products commenting on the same line looked like duplicated work, and we
still cannot say whether it is, because nobody has read the text. The quieter
cross-product boundary looked like a general property of crossing a boundary,
until we split the matched pairs by author product and found most of the size
sitting in two of them. And when we applied our own rules to a large review
corpus assembled by other people, every candidate pull request turned out to
already be in ours, so the replication gate failed rather than passed. We keep
all of it in Online Resource~1. A paper that reports only what survived is not
reporting a method.

\subsection{One lever that does hold}

Against that background, the issue link is the exception worth acting on.

A pull request that says which issue it belongs to is answered across a product
boundary about twice as often as one that does not. The same link changes
nothing when the reviewer shares the author's product. It survives a
within-repository comparison, a shuffled label, and dropping the projects that
contribute most.

The reading that fits is unglamorous and useful. Inside one product the loop can
close without anyone reconstructing why the change exists. Across the boundary
somebody has to do that reconstruction, and a link to the issue is the cheapest
way we can observe of handing it to them. This is what reviewers are known to do
first: orient themselves to context and rationale before deciding anything
\citep{heander2026decisionmaking}, using references in the discussion to build
common ground \citep{chopra2021referencing}. We cannot prove the link causes the
answer, but it is a pre-trigger property of the change, it costs one line, and
nothing else we measured behaves this way.

\subsection{What to build, and what to stop counting}

\textbf{Platforms should record the edge, not only the actors.} A review tool
should store what a message replies to, which batch it came from, which run
produced it, and who is expected to act next. Our whole method exists because
those four fields are missing or ambiguous, and a timestamp alone cannot
separate a burst of parallel events from a handoff. This is a small schema
change with a large effect on what anyone can later measure.

\textbf{Agents should hand over context, not just output.} The clearest observed correlate of a crossed-boundary response in our data is
whether the pull request says what it is for. Neither vendor nor maintainer
wholly controls that, since a description can be written by either and edited
afterwards, and the association is observational. Writing the issue reference into the body is close to free
and it is the only lever in this study that survived every check we could think
of.

\textbf{Agents should be able to say what they did with a review point.} Marking
a point as received, declined, routed, or awaiting a person turns an inferred
sequence into a record. The scarcity of different-product relays says plainly
that installing two products together does not create that record by itself.

\textbf{Evaluation should ask for a connection, not a count.} An answered review point is a more specific field signal than a merge, because it
is machine-checkable and it happens before the outcome. More specific is not the
same as more predictive, and our placebo exposures show it is not more
predictive: looser reply signals carry the same association. It is also rare, so it
belongs in auditing rather than in a score. Nothing here licenses treating it as
a quality metric, and a real test would randomise an acknowledgement feature and
watch what happens.

\textbf{Researchers should stop reporting co-presence.} If a study counts
products on a pull request, it is measuring installation, not collaboration. The
ladder in this paper is one way to be specific; any way is better than a count.
This bears on a live argument. It has been proposed that agents can already meet
every goal of code review, and that keeping a person as the mandatory reviewer is
a dead end \citep{monperrus2026endofreview}. On this evidence the person is not a
formality layered on an agent loop. In the public trace, user activity is the dominant visible bridge.

\section{Threats to Validity}\label{sec:threats}

\textbf{What we can see.} Only inline review comments carry a reply target, so
the addressed edge can never be built for a review summary or a comment on the
pull request itself. Those two channels are 57.1\% of what reviewers write on our trigger PRs, and
44.0\% of cross-product review episodes arrive through them. No
threshold recovers that share; the release records no reply target for such comments. A
coarse count of any later PR-level comment suggests the unseen episodes are not quiet, since about 36\% of them see some
later comment inside 48 hours. But that count cannot tell an answer from a
passing remark, so we use it to size the blind
spot and not to estimate anything inside it.

The event tables also do not cover the same PRs. A missing row can mean there was
no event, or that the event was not captured. Ordinary
commit and review timeline rows carry no usable time in this release. So we
make claims about timing only for event types that do carry a usable time. We
also treat a force-push as branch movement, not as a checked fix.

\textbf{Identity and meaning.} Our list of approved accounts is strict, so it may miss some agent accounts. A
GitHub \texttt{User} account does not prove that a person worked alone, and it
does not prove a person at all: an account can be scripted. We tested that
directly on the 80 accounts that write the edges, scoring each for repeated
template text, regular timing, round-the-clock posting, and volume, with
thresholds fixed in advance. One account trips two or more of them, and dropping
it leaves the estimate where it was. Reading the flagged cases showed the
heuristics were mostly catching people, not scripts: the repeated strings are
hand-typed agent invocations and GitHub's own button text. An exact reply target proves that someone addressed the
point. It does not prove understanding, agreement, or repair. We never see
private messages, prompts, or shared memory.

\textbf{Which PRs we kept.} The hour-48 check point keeps only PRs that are
still open at that moment, and most cross-product inline-trigger PRs close before
then. The hour-48 numbers therefore describe slower PRs. The whole-population curves in Figure~\ref{fig:relay} are our answer to this:
they use every trigger PR, and they still show the same direction, though a much
smaller gap. Shorter reply windows raise a
further problem, because a reply inside such a window could itself change whether
the PR is still open at hour 48. We treat those windows as extra checks only, and
the 48-hour window is the main one.

\textbf{What the edge means.} An exact reply target records that someone replied
on the trigger's thread. It does not record who. In this group that someone is
almost always a user account, so RQ3 measures a person attending to an agent's
review point, not one product handing over to another.

It also records less than its name suggests. Placebo exposures show that a reply
anchored anywhere else on the pull request carries the same association, and that
shuffling which comment each reply hangs on does not move the estimate. So the
anchoring is not the active ingredient, and a reader should take our RQ3 result as
being about a human reply inside the window rather than about a specific
connection. What the reply says does separate: restricting the exposure to the 56
substantive replies reproduces the headline, while the 15 one-click hand-offs give
a smaller estimate on an interval spanning zero. With 15 such PRs we cannot
distinguish the two subsets statistically, and we do not claim a routing click is
inert.

The reply identifier is looser than the name suggests. It points at the first
comment of a thread, so our edge means ``a reply in the thread the trigger
opened''. Two things follow, and we measured both. First, the exposure can only
fire when the trigger is itself the first comment of its thread. Among cross-product inline triggers that is almost always true: 13 of the 3,526
in the thread-position cohort sit mid-thread. The hour-48 cohort is a different
population rather than a subset of that one, and 3 of its 1,067 sit mid-thread,
none of them exposed.
The restriction bites hard for same-product triggers across the whole release,
where 46\% sit mid-thread. Inside the 546 matched pairs it is milder, 12 of the
253 same-product triggers that are inline at all, but it runs one way: no
cross-product trigger is blocked where its partner is not. That is why the reply
row of Figure~\ref{fig:bridge} uses the pairs where both sides can produce it. Second, inside a thread with several replies, a later reply may be
answering an earlier reply rather than the trigger. Among the 109 exposed PRs,
92 have exactly one reply in the thread, so for those the reply can only be
answering the trigger. For the remaining 17 we cannot tell.

\textbf{Selection and cause.} Matching holds several visible factors fixed, and
the outcome models use pre-trigger controls and repository-aware intervals.
They cannot balance what a review meant, how hard the task was, what the
maintainer intended, or what happened in private.

The stress test puts a limit on this. A hidden cause weaker than an E-value of
2.27 cannot account for the edge result. A stronger one still could. And the
before-the-fact user-activity check shows that selection of this kind is
present in our data, and only partly measured. Our controls also include no
stand-in for task difficulty. The later-state findings stay associations.

\textbf{How far the results reach.} AIDev-pop covers public repositories with
more than 100 stars, and the product pairs are uneven. Leave-one-out checks ease
the worry that a few repositories or a few pairs drive the result, and no single
one flips a sign. They do not make the results uniform. The matched cross-product
gap is concentrated by author product, with most of its size in two strata and the
rest close to zero, so it should be read as something this release shows for
particular products. The five-minute burst window is a convention rather than a
boundary we found in the data, and although the RQ1 ordering survives every cut we
tried, the size of the lead moves between 19 and 41 points depending on the
window. They do
not extend it to private projects or to future versions of these products. The
outside dataset we screened checks our schema and identities, but after
removing overlap it gives no independent group for RQ3.

\section{Conclusion}\label{sec:conclusion}

Two AI products on one pull request is not proof of teamwork. Once the fast
burst of events is set aside, product co-presence almost never becomes one
product answering another. User accounts form the main visible bridge, and among the accounts we observe
bridging, most have reviewed in that repository before.

The clearest connected signal is a reply, and four times in five a user account
writes it. What carries the association is that somebody came back before the
later state, not where on the page the reply was attached: an off-target reply
does as well, and shuffling the anchor leaves the estimate where it was. The
exact anchor still earns its place, because it is what lets us name the account
and read what it wrote. It buys attribution, not prediction, and a count of
products buys neither. Field evaluation of multi-agent work should ask, beyond mere co-presence, for three things: an addressed edge, a visible owner, and a later state.
